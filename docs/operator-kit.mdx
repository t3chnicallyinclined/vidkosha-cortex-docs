A practical checklist for operators: get WAL + Helix healthy, then iterate on services (ingest, projection, corpora/snapshots, retrieval, tools).

## 0) Pick your operator role (service) {#0-pick-your-operator-lane}

- **Ingest operator:** bring new sources into the WAL.
- **Projection/index operator:** consume WAL events and update Helix.
- **Snapshot builder / storage operator:** seal archival snapshots and serve retrieval.
- **Tool/MCP operator:** provide deterministic transforms/rendering steps.
- **Compute operator (optional):** embeddings and/or inference.

If you’re starting from zero, the lowest-risk path is: *projection/index + snapshot serving*.

## 1) Make the WAL boring

- Confirm JetStream durability and retention policy (hot window target).
- Ensure publishers fail loudly when JetStream is unhealthy.
- Track consumer lag and set an SLO for “time to projection”.

Observability baseline (operators should treat this as required):

- WAL publish rate / error rate
- consumer lag per projection consumer group
- storage usage vs retention policy

## 2) Make Helix queryable

- Build at least one projection that answers a real user question quickly.
- Make your projection idempotent and replay-safe.
- Keep schema/version fields explicit so you can backfill.

Query + serving observability:

- retrieval latency p50/p95/p99 (hot vs cold)
- error rates by service class (snapshots/tools/embeddings)
- SLO compliance by operator capability tier

## 3) Add paid history (archives)

- Decide snapshot boundaries (topic + time range + recipe pins).
- Seal snapshots with an integrity manifest.
- Serve snapshots on demand and emit usage events.

Reference:

- [Corpora, streams, and snapshots](/docs/packs)

If you want a clean operator business, wire dashboards to usage events so you can answer:

- which service generated revenue
- which customers/topics are hot
- which SLO tier is actually being purchased

Canonical economics + flow:

- [Canonical: 7-day WAL freshness + archival market](/docs/canonical-drag)

## 4) Secure the fabric (NATS nkeys)

The operator-side security model to target is: **fast rotation, least privilege, and “deny by default” subject access**.

Minimal posture:

- **NATS identity via nkeys** for operators.
- **Least-privilege permissions** (publish/subscribe allowlists), scoped to exactly what an operator provides.
- **Easy revocation/rotation:** if you suspect compromise, rotate keys and cut the operator out of routing.

Practical policy design:

- separate subject families: ingest facts vs mission/work requests vs metering/settlement
- use subject patterns to enforce boundaries: tenant/topic scoped subjects
- default to read-only when possible (e.g. snapshot-serving operators subscribe to request subjects and publish responses + usage events)

Key separation:

- one identity for NATS transport permissions
- a separate identity for economic settlement (chain signatures)

## Optional: retention tiers (30d / 90d / 1y) {#optional-lane-retention-tiers-30d--90d--1y}

Beyond the baseline hot window, operators can offer “deeper memory” tiers by retaining and serving archival snapshots for longer windows (priced by storage + replication + latency tier).

This is a simple ladder:

- 7d freshness (baseline)
- 30d retention (mid-tier)
- 90d/1y retention (premium)

The community/DAO can decide which tiers are default and what gets subsidized.

## Optional: host an MCP server {#optional-lane-host-an-mcp-server}

Run tools agents can call reliably (retrieval, transforms, render steps) so end-to-end automation becomes a metered, auditable service.

## Optional: semantic media archives {#optional-lane-semantic-media-archives}

Ingest/transcribe/embed curated YouTube/podcasts and serve them as a topic corpus for semantic search.
