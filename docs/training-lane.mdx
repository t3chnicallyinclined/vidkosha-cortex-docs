This page describes the “operator-run training” vision: **Vidkosha Cortex routing training and fine-tuning jobs to accelerator-backed operators**, the same way it routes retrieval, tools, and storage.

This is a *lane design* and a *why-it-fits-the-architecture* explanation. Not all of it is implemented today.

## Why training belongs in the fabric

Training becomes viable for a decentralized operator network when three things are true:

- **Work is legible:** jobs are explicit units with IDs, inputs, outputs, and SLOs.
- **Inputs are reproducible:** datasets are referenced by pack IDs + integrity manifests.
- **Settlement is enforceable:** usage events can be verified and aggregated into payouts.

Those are already the core primitives of the WAL + packs + marketplace design.

## The three-plane mapping

### Write plane (WAL)

Training introduces new event lanes:

- job requests (fine-tune, full-train, eval)
- dataset references (pack IDs + manifests)
- tool step requests (preprocess, shard, augment)
- results (model artifact hashes, eval summaries)

Why this is powerful:

- you can replay and audit “what was trained on what”
- you can account for compute work without trusting a single provider

### Read plane (Helix)

Helix becomes the index of training provenance:

- dataset packs and their coverage (topic/time)
- job runs (inputs, recipe pins, operator identity)
- model artifacts (hashes, metadata, evaluation summaries)

This makes it possible to query:

- “Which model artifact was produced from which dataset pack?”
- “What is the latest eval status of model X?”

### Execution plane (operators)

Training operators are providers with real accelerator capacity — “Vidkosha Cortex behind a datacenter of accelerator servers” (Cerebras-class or GPU clusters).

Operator responsibilities:

- accept job requests and price them
- run deterministic preprocessing steps (prefer MCP/tool workflows)
- execute training/eval
- publish artifact manifests and usage events

## Scaling story (Netflix/gaming-class intuition)

This lane scales the same way the rest of the fabric scales:

- **shard by subject:** tenant/topic/job class/time bucket
- **route by policy:** price + SLO + geography
- **scale by adding providers:** more operators → more concurrent jobs

The key is that the WAL stays the coordinator: it’s the source of truth for what was requested and what was produced.

## Operator thesis (why this works economically)

The fabric works because operators provide **valuable services** with explicit SLOs (not opportunistic peer discovery).

That matters because many decentralized storage patterns (IPFS-like) can have high tail latency for interactive access; for training/eval, the analog is unpredictable data access and non-reproducible inputs.

Here, operators earn because they deliver measurable utility (preprocessing, training/eval, artifact serving) and the network can meter and settle it.

## Economics (how operators get paid)

Training is expensive, so pricing has to be explicit:

- **compute metering:** time/steps/tokens/bytes processed (lane-specific)
- **SLO tiers:** latency/availability commitments priced separately
- **artifact serving:** optional paid hosting of model artifacts

This plugs into the same settlement machinery as other lanes:

- [Marketplace + payouts](/docs/operator-marketplace)

## Relationship to the 7-day hot window

Training inputs should reference **archival packs**, not ephemeral hot history.

The 7-day WAL retention boundary stays a feature:

- hot window stays bounded and cheap
- long-term datasets live as integrity-checked packs with explicit funding
