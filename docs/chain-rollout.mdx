title: Chain rollout (CKB dev testnet flip)
---

Chain integration is a core part of the Vidkosha Cortex end-state: **verifiability + registry + settlement** anchored on **Nervos CKB**.

Today, chain integration is still **gated during buildout** (feature-flagged and safe modes like log-only).

**Flip moment:** we go *live* when we enable real anchoring on **CKB dev testnet**.

The goal is to keep the hot path fast while making the system externally verifiable: do real work off-chain, but make the outcomes auditable on-chain.

For stakeholders: this lowers adoption risk and accelerates credible go-to-market.

For operators: this keeps latency, complexity, and operational overhead under control.

## Design principles

- **Hash-only on-chain:** store commitments (roots/hashes), not raw data.
- **Keep the hot path off-chain:** low-latency retrieval and operator work stay off-chain; the chain provides auditability and settlement.
- **Minimize on-chain surface:** anchor only what you need to prove history, identity, and payouts.
- **CKB-first implementation:** Nervos CKB is the reference rail for chain integration.

## What we anchor on-chain (at go-live)

The chain layer is for *commitments* and *settlement*, not for serving data.

Typical candidates for anchoring:

- **Payout batch commitments:** a Merkle root or digest of usage-event aggregation and payout allocations.
- **Snapshot manifest commitments:** hashes of archival snapshot manifests (integrity + provenance checkpoints).
- **Operator identity registry (optional):** a minimal registry for operator keys and metadata, if useful.

None of the above requires on-chain execution for the hot path.

## Phased rollout (operator-friendly)

### Phase 0: Gated buildout (today)

- Operators run services and emit usage events.
- The network aggregates usage into payout batches off-chain.
- Chain integration exists behind safe gates (feature flag + env + log-only / mock modes).

This phase is enough to launch paid APIs and operator businesses.

### Phase 1: Checkpointing (hash-only)

- Periodically anchor **payout batch roots** (and/or snapshot manifest roots) on-chain.
- Keep the payout execution off-chain.

Benefit: external parties can verify that batches weren’t rewritten after publication.

### Phase 2: Optional settlement on-chain

- Add an option to settle payout batches on-chain.
- Keep “who gets paid how much” derived from the same usage-event roots.

This is a credibility upgrade, not a requirement.

### Phase 3: Stronger enforcement (only if needed)

If the market demands it, introduce stronger enforcement mechanisms (carefully):

- staking requirements for certain services/SLO tiers
- operator allowlists and stronger audit windows
- (future) escrow/slashing/dispute-game complexity only if/when third-party operators are enabled

These are higher complexity and should be introduced only when the volume and adversarial pressure justify it.

## Operator impact

At go-live, operators and network services should expect a chain dependency for chain integration.

That does **not** mean every request executes on-chain. It means the network can:

- publish commitments for payout batches and manifests
- read a registry for operator identity and payout routing
- (optionally) settle on-chain when that mode is selected

At most, chain integration should require:

- reading checkpoint events (batch roots) for verification
- optionally participating in settlement if they choose that payout mode

## Off-chain mode (self-hosted)

Vidkosha Cortex can also be deployed as an off-chain knowledge fabric for personal/company use cases:

- same WAL-first + rebuildable projections architecture
- no requirement to anchor or settle on a chain

This is useful when you want the stack (NATS WAL + Helix projections + operator services) without tying your deployment to external settlement.

## Stakeholder view (why this sequencing matters)

This rollout order is about de-risking:

- build demand and revenue with off-chain metered APIs
- harden auditability with hash-only commitments
- add settlement only when the network has enough real usage to justify the overhead
