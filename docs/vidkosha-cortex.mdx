Vidkosha Cortex is an operator-run DRAG (Decentralized RAG): a low-latency knowledge fabric built from a WAL-first write plane, rebuildable read projections, and a metered operator execution plane — with **verifiability and settlement anchored on Nervos CKB**.

Chain integration is currently gated during buildout. The “flip moment” is **go-live on CKB dev testnet**.

## What DRAG enables

- **Humanity’s Open Knowledge:** Wikipedia/Wikidata + open research + standards + public datasets.
- **Freshness as a feature:** “Newest papers on X” and “What changed today?” becomes a default workflow.
- **Real-time market intelligence:** news + filings + research feeds can be sifted and queried as they arrive.
- **RAG at scale:** semantic search + graph neighborhood hydration (Helix) for grounded answers.

DRAG is the **retrieval** substrate: low-latency, grounded context with provenance.

## Decentralized inference + specialized agents (execution plane)

Separate from DRAG, Vidkosha Cortex is also a decentralized **execution** fabric: operators can run specialized agents and workflows (MCP tools, transforms, inference) as metered services.

- **Agents + MCP workflows:** toolcalls + deterministic transforms + verifiable outputs.
- **Decentralized inference services:** operators package workflows as callable endpoints (retrieval + tool steps + optional inference).

Illustrative applications:

- **Automated content pipelines:** research → script → voice → clips → stitched output (10–30s segments).
- **Semantic media archives:** transcribe + embed long-form media and serve grounded search as corpora.
- **SEO packaging:** upload long content and generate a packaging bundle (titles, chapters, descriptions, keywords, clip plan, thumbnail concepts).

## Why Vidkosha Cortex is different

Most “decentralized RAG” attempts accidentally build a **decentralized storage network** and then try to bolt interactive retrieval on top.

That tends to produce high tail latency because you pay for discovery + multi-hop routing + variable availability (IPFS-style patterns), and you’re often retrieving cold content that isn’t pinned near the user.

Vidkosha Cortex is a **service fabric**:

- **Fast hot path:** indexed retrieval over a bounded freshness window.
- **Explicit cold path:** paid archival snapshots served by storage operators with clear expectations.
- **Real operator businesses:** operators aren’t rewarded for “having a CID” — they earn because they deliver low-latency services that the network can meter and settle.

## The “Thinking Fabric” idea (and where the name comes from)

We often describe Vidkosha Cortex as a **Thinking Fabric**: a network where knowledge is continuously ingested, indexed, served, and improved by operators — with replayable history and measurable work.

The name “Vidkosha” is a mash-up of two Sanskrit terms:

- **Vidyā**: knowledge, learning, cultivated understanding
- **Kośa**: a treasury/storehouse (and, in some Vedānta contexts, a “sheath” or layer)

In engineering terms, the metaphor maps to a contract:

- **Cultivation:** operators continuously ingest and refine into indexed projections.
- **Preservation:** append-only history (WAL + snapshots) makes state replayable.
- **Transmission:** manifests + commitments let others verify provenance.

The goal is calm, legible systems: clarity, provenance, memory, and iteration — implemented with modern distributed-systems primitives.

## Architecture in one picture (the three planes)

- **Write plane (truth):** NATS JetStream as the WAL (durable, replayable).
- **Read plane (speed):** Helix as the rebuildable query projection.
- **Execution plane (work):** operators run ingestion, indexing, corpus/snapshot serving, tools/MCP steps, embeddings/inference, and later training.

Plain English: **WAL = “receipt tape”**. Everything that happens gets appended to a log first, and the rest of the system is built by replaying that log.

Why this scales like Netflix/large streaming systems:

- append facts once → fan out to many consumers
- scale by adding consumers/operators, not by rewriting the producer
- rebuild anything by replaying the log + snapshots

## Why Nervos CKB

CKB is the anchoring rail because it is designed as a **Common Knowledge Base**: a minimal, verifiable substrate where commitments can live without dragging the hot path onto the chain.

What we lean on:

- **Cell model + capacity economics (CKBytes):** storage is explicitly scarce and priced; commitments live as minimal on-chain state.
- **Scripts (lock/type) on CKB-VM (RISC-V):** verification logic is flexible without requiring a heavy smart-contract stack.
- **PoW security + state-size discipline:** the model pushes long-term state pressure into an explicit economic system.

## Latency + scale (what we optimize for)

The design target is an **interactive hot path** that can reach *double-digit millisecond* response times when operators are deployed close to users and the query stays within the hot window.

Mechanically, that comes from:

- **precomputed projections** (Helix) instead of raw-log scanning
- **service routing** (choose providers by SLO + price + geo) instead of peer discovery
- **bounded hot storage** (e.g. 7d) so performance doesn’t degrade as the network grows

The cold path (paid history) is allowed to be slower because it’s explicit, priced, and integrity-checked.

## Why NATS (JetStream)

JetStream is the write plane because it’s a pragmatic, scalable WAL with durable consumers:

- append once, fan out to many operators
- bounded retention economics (hot window)
- replay to rebuild projections deterministically

## Observability-first operations (a hidden superpower)

Because the fabric is WAL-first and work is routed as explicit missions, operators get unusually clean observability:

- JetStream health + consumer lag tells you “is the network ingesting and projecting?”
- per-service latency (p50/p95/p99) tells you “is retrieval/tools/inference meeting SLOs?”
- usage events tie performance to payouts (“what actually generated revenue?”)

Two practical consequences:

- **Lagging topics become visible demand:** operators can see which services are behind and add capacity to earn.
- **Semantic demand signals (aggregate):** operators can see what’s being asked for as topic/cluster aggregates (not raw prompts), so they can build and deploy the right endpoints.
- **Discovery stays sane (future):** NATS wildcards help routing/ops; catalog indexing can be added later if/when an open operator set is enabled.

This is the practical difference vs opaque AI stacks: you can run Grafana dashboards, see exactly where time/cost is spent, and tune routing, caching, snapshot replication, and recipe/version rollouts with confidence.

## Layered retention tiers (community-defined storage tiers)

The 7-day hot window is the baseline, but the network can support **retention tiers** as a market:

- Tier 1: 7d freshness (cheap, fast)
- Tier 2: 30d retention (more coverage, more cost)
- Tier 3: 90d / 1y retention (premium)

Operators who retain more history charge more; the community/DAO can decide defaults, replication factors, and what gets subsidized.

## Inference, tools, and “real operator revenue”

The network’s moat is not just “retrieval exists” — it’s that workflows are **metered services**:

- snapshot serving (hot/cold)
- transforms/rendering via MCP tools
- embeddings and inference (optional services)

This is what makes operator rewards sustainable: there are clear, valuable services users pay for.

Design goal: those services are accessible via **stable, metered APIs** (retrieval, embeddings, tools/MCP steps, and inference endpoints), so operators can build revenue-generating products on top of the fabric instead of relying on one-off consulting.

## Off-chain mode (self-hosted)

Vidkosha Cortex can also be deployed as an off-chain knowledge fabric for personal/company use cases:

- same WAL-first + rebuildable projections + operator services
- no requirement to anchor commitments or settle on a chain

This mode is useful when you want the stack and the discipline without tying your deployment to external settlement.
